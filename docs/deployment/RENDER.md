# Deploy on Render

How Origen is deployed to Render for the academic delivery (#292), and how a merge to `main` reaches production.

**Status:** configuration prepared. The Render account, the first deploy and the acceptance checks of `ACEPTACION_HOSTING_ACADEMICO.md` are still pending.

## How a deploy happens

1. A pull request is merged into `main`.
2. `.github/workflows/cd.yml` runs on the push to `main` and calls the Render deploy hook with the merged commit (`ref=<sha>`).
3. Render builds the `Dockerfile` (an Elixir release).
4. Render starts `/app/bin/server`, which runs `/app/bin/migrate` first and then the web server. If a migration fails, the server never starts, the new version never answers the health check on `/`, and Render does not switch traffic to it.

Render's own Git auto-deploy is off (`autoDeployTrigger: "off"` in `render.yaml`), so the workflow is the only automatic trigger. It can also be run by hand from the Actions tab (`workflow_dispatch`).

After the hook call succeeds, the workflow tags the commit with the next semantic version, computed from the Conventional Commits since the last version tag (`.github/scripts/next-version.sh`): a breaking change (`type!:` or a `BREAKING CHANGE:` footer) bumps the major, any `feat` bumps the minor, anything else bumps the patch; the first one is `v1.0.0`. The tag records that a deploy was **requested** for that commit; whether it went live is shown in the Render dashboard. A commit that already has a version tag is not tagged again. The tag runs in its own job (`tag`), the only one with write access to the repository; if it fails, use **Re-run failed jobs** so the deploy hook is not called again. Earlier date tags such as `v2026.11.11-3` are kept and ignored when computing versions. Script tests: `bash .github/scripts/next-version.test.sh`.

## What `render.yaml` creates

| Resource | Name | Plan | Notes |
| --- | --- | --- | --- |
| Web service | `origen` | `free` | Docker runtime, region `virginia`. Sleeps after 15 minutes without traffic; the next request takes about a minute to wake it. |
| Postgres | `origen-db` | `free` | Postgres 17, 1 GB, internal connections only. **Expires 30 days after creation** (14-day grace period), then Render deletes it with its data. |

Both are in the same region so the app reaches the database over Render's private network.

Free plans need no payment method (checked with `render blueprints validate`).

## Moving to paid plans

Before the free database expires, or when the app must not sleep:

1. Add a payment method to the Render workspace.
2. In `render.yaml`, set the web service `plan` to `0.5c-512mb` and the database `plan` to `0.1c-256mb`, and add `diskSizeGB: 1` to the database (otherwise it defaults to 15 GB).
3. Optionally add `preDeployCommand: /app/bin/migrate` to the web service and remove the migrate call from `rel/overlays/bin/server`, so a failed migration stops the deploy before the new version starts.

Upgrading the existing free database in place keeps its data; letting it expire does not.

## One-time setup

1. In Render: **New > Blueprint**, pick this repository and the `main` branch. Render reads `render.yaml`.
2. Fill the variables marked `sync: false` when Render asks for them:
   - `SECRET_KEY_BASE`: output of `mix phx.gen.secret`.
   - `ORIGEN_TOTP_KEY`: output of `openssl rand -hex 16` (exactly 32 characters). Keep a copy in the team's password manager: if it changes, the TOTP seeds already stored cannot be decrypted.
   - `ORIGEN_VERIFIER_KEY` is generated by Render.
3. In Render, open the `origen` service > **Settings > Deploy Hook** and copy the URL. Treat it as a secret: anyone with it can trigger a deploy.
4. In GitHub: **Settings > Environments > New environment** named `production`, and add the secret `RENDER_DEPLOY_HOOK_URL` with that URL.
5. Optional: under that environment, add required reviewers if the team wants a manual approval before each deploy.

## Create the first Administrator

The original first-admin bootstrap stays disabled in `:prod` (`FIRST_ADMIN_BOOTSTRAP.md`). The team chose a simpler operator command instead of the two-person approval designed in #452: `bin/issue_admin_invitation` creates the first Administrator as `pending_activation` and prints a single-use activation link (valid 24 hours). The account holder opens it, sets a password and enrolls TOTP. There is no email provider, so the operator hands the link over.

The free Render plan has no shell, so the command runs from the operator's machine with the same release image, against the database's external URL.

1. **Build the image of the deployed commit** (the one on `main`):
   ```bash
   git switch --detach origin/main && docker build -t origen:ops .
   ```
2. **Open the database to your IP, temporarily.** Render > `origen-db` > **Access Control**: add your public IP. `render.yaml` keeps `ipAllowList: []`, so this is a manual, temporary exception.
3. **Write the environment to a file only you can read**, never on the command line (it would stay in the shell history):
   ```bash
   umask 077 && touch ~/origen-ops.env
   ```
   Keep it outside the repository. Fill it with, copied from the Render dashboard:
   - `DATABASE_URL`: `origen-db` > **External Database URL**.
   - `SECRET_KEY_BASE`, `ORIGEN_TOTP_KEY`, `ORIGEN_VERIFIER_KEY`: the same values as the `origen` service. `ORIGEN_VERIFIER_KEY` must match, or the link will not activate.
   - `DATABASE_SSL=true` (the external URL requires TLS) and `ORIGEN_OPERATOR_INVITATION_ENABLED=true`.
4. **Run the command** with the service's public host:
   ```bash
   docker run --rm --env-file ~/origen-ops.env origen:ops /app/bin/issue_admin_invitation --host origen-4kju.onrender.com
   ```
   It prints the **login identifier** (the account id; this account has no email), the expiry and the activation link. It refuses with `administrator_exists` if an Administrator already exists.
5. **Hand the link only to the account holder**, through a private channel. Whoever has the link can activate the account until it is used or expires.
6. **Clean up:** delete `~/origen-ops.env`, remove your IP from `origen-db`, and clear the terminal scrollback (the link was printed there).
7. **Account holder:** open the link, set a password (at least 12 characters), scan the QR code with an authenticator app and enter the code. Then sign in at `/login` with the account id, the password and a TOTP code. With the [academic demo mode](#academic-demo-mode-password-only) on, there is no QR code or TOTP code: only the password.

If the link expires or is lost before activation, issue a new one for the same pending account; the previous link stops working:

```bash
docker run --rm --env-file ~/origen-ops.env origen:ops /app/bin/issue_admin_invitation --host origen-4kju.onrender.com --account-id <id>
```

Once the account is `active`, the command refuses (`administrator_active`); further staff accounts are created by the Administrator from the app.

If it fails with `audit_unavailable`, the account was created but the link was not printed and was revoked, because the handoff could not be audited. The error names the pending account id: run the command again with `--account-id <id>`.

## Academic demo mode (password only)

`render.yaml` sets `ORIGEN_ACADEMIC_DEMO_PASSWORD_ONLY=true` so professors can try the app as internal staff (Administrator, Professional, Secretary) with only a login identifier and a password. `config/runtime.exs` turns the mode on only when the variable is exactly `true`; it is off everywhere else, including local development and tests, unless set.

**This is a deliberate security gap.** It removes the second factor from every internal account on this instance. Use it only with fictitious data. Before any real patient or clinic data reaches the instance, remove the variable (or set it to `false`) and redeploy.

With the mode on:

- `/login` asks only for the identifier and the password. Wrong passwords, deactivated accounts and roles without access are still rejected, and every attempt is still audited (`internal_login`).
- Activating an account (`/activar` for staff, `/administrador/activar` for the first Administrator) asks only for the password and its confirmation (at least 12 characters). The app still generates and stores an encrypted TOTP secret, because the database requires one for every active account, but it does not show the QR code or ask for a code.
- Patients and the patient magic link are not affected.

Turning the mode off later restores TOTP on the next sign-in, but accounts activated in demo mode never saw their QR code, so those holders cannot produce a code. Recreate those accounts (or reissue their invitations) after turning the mode off.

### Accounts for the professors

There is no email provider, so every link is handed over by hand, through a private channel.

1. **First Administrator:** follow [Create the first Administrator](#create-the-first-administrator). The holder opens the link and sets a password. This account has no email: its login identifier is the account id that `bin/issue_admin_invitation` prints.
2. **Professionals and secretaries:** the Administrator signs in, opens `/administrador/cuentas`, enters the person's email and role, and issues the invitation. The screen shows the activation link (**Enlace de invitación**) to copy; the app does not send it. If the link expires or is lost, use **Reemitir** on the same screen; the previous link stops working.
3. Each person opens their link, chooses a password, and signs in at `/login` with their email and that password.

## Known limits

- **First Administrator by operator command.** The first Administrator is created with the procedure above, not with the two-person approval of #452: one operator issues it, and the activation link is printed in the operator's terminal. Issuance and activation are audited.
- **Single database user.** The app connects with the user Render creates. The hardened role model of `priv/repo/security/provision_roles.sql` (owner, migrator, runtime, verifier) is not applied; the migrations already skip their role grants when those roles do not exist.
- **Academic demo mode is on.** Internal staff sign in without TOTP; see [Academic demo mode](#academic-demo-mode-password-only). Fictitious data only.
- **No outgoing email provider.** `config/runtime.exs` keeps the production mailer block commented out, so no email provider is configured.
- **CI does not gate the deploy.** CI runs on pull requests, so the code reaching `main` already passed it. A direct push to `main` would deploy without CI.
