# Deploy on Render

How Origen is deployed to Render for the academic delivery (#292), and how a merge to `main` reaches production.

**Status:** configuration prepared. The Render account, the first deploy and the acceptance checks of `ACEPTACION_HOSTING_ACADEMICO.md` are still pending.

## How a deploy happens

1. A pull request is merged into `main`.
2. `.github/workflows/cd.yml` runs on the push to `main` and calls the Render deploy hook with the merged commit (`ref=<sha>`).
3. Render builds the `Dockerfile` (an Elixir release).
4. Render starts `/app/bin/server`, which runs `/app/bin/migrate` first and then the web server. If a migration fails, the server never starts, the new version never answers the health check on `/`, and Render does not switch traffic to it.

Render's own Git auto-deploy is off (`autoDeployTrigger: "off"` in `render.yaml`), so the workflow is the only automatic trigger. It can also be run by hand from the Actions tab (`workflow_dispatch`).

After the hook call succeeds, the workflow tags the commit as `v<YYYY.MM.DD>-<run number>` (UTC), for example `v2026.11.11-12`. The tag records that a deploy was **requested** for that commit; whether it went live is shown in the Render dashboard. A manual re-run on an already tagged commit does not add a second tag.

## What `render.yaml` creates

| Resource | Name | Plan | Notes |
| --- | --- | --- | --- |
| Web service | `origen` | `free` | Docker runtime, region `virginia`. Sleeps after 15 minutes without traffic; the next request takes about a minute to wake it. |
| Postgres | `origen-db` | `free` | Postgres 17, 1 GB, internal connections only. **Expires 30 days after creation** (14-day grace period), then Render deletes it with its data. |

Both are in the same region so the app reaches the database over Render's private network.

Free plans need no payment method (checked with `render blueprints validate`).

## Moving to paid plans

Before the free database expires, or when the app must not sleep:

1. Add a payment method to the Render workspace.
2. In `render.yaml`, set the web service `plan` to `0.5c-512mb` and the database `plan` to `0.1c-256mb`, and add `diskSizeGB: 1` to the database (otherwise it defaults to 15 GB).
3. Optionally add `preDeployCommand: /app/bin/migrate` to the web service and remove the migrate call from `rel/overlays/bin/server`, so a failed migration stops the deploy before the new version starts.

Upgrading the existing free database in place keeps its data; letting it expire does not.

## One-time setup

1. In Render: **New > Blueprint**, pick this repository and the `main` branch. Render reads `render.yaml`.
2. Fill the variables marked `sync: false` when Render asks for them:
   - `SECRET_KEY_BASE`: output of `mix phx.gen.secret`.
   - `ORIGEN_TOTP_KEY`: output of `openssl rand -hex 16` (exactly 32 characters). Keep a copy in the team's password manager: if it changes, the TOTP seeds already stored cannot be decrypted.
   - `ORIGEN_VERIFIER_KEY` is generated by Render.
3. In Render, open the `origen` service > **Settings > Deploy Hook** and copy the URL. Treat it as a secret: anyone with it can trigger a deploy.
4. In GitHub: **Settings > Environments > New environment** named `production`, and add the secret `RENDER_DEPLOY_HOOK_URL` with that URL.
5. Optional: under that environment, add required reviewers if the team wants a manual approval before each deploy.

## Known limits

- **No first Administrator yet.** `config/runtime.exs` disables the first-admin bootstrap in `:prod` on purpose (see `FIRST_ADMIN_BOOTSTRAP.md`). After the first deploy the app runs, but there is no supported way to create the first internal account until the team decides how to do it under the controls of that runbook.
- **Single database user.** The app connects with the user Render creates. The hardened role model of `priv/repo/security/provision_roles.sql` (owner, migrator, runtime, verifier) is not applied; the migrations already skip their role grants when those roles do not exist.
- **No outgoing email provider.** `config/runtime.exs` keeps the production mailer block commented out, so no email provider is configured.
- **CI does not gate the deploy.** CI runs on pull requests, so the code reaching `main` already passed it. A direct push to `main` would deploy without CI.
